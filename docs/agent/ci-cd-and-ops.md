# CI/CD + operational hardening

The automation that backs the main-only workflow (`main` is the only branch; staging was abandoned 2026-10-03). Everything here is committed and ready; the pieces that need an external account stay inert (logging a warning and skipping) until you add the secret or variable noted below.

## The workflow at a glance

```
work on a short-lived branch  ->  open a PR to `main`  ->  CI must be green  ->  merge  ->  merge = push to `main` rebuilds production
                                                                 |
                                                  Sanity backup runs nightly
                                                  uptime check runs hourly
```

Every change goes through a **pull request** so CI gates the merge and the PR template's definition-of-done travels with every change. Required checks are `build` and `test`; squash-merge keeps history linear.

## What runs in CI (`.github/workflows/ci.yml`)

Runs on every PR, on pushes to `main`, and by hand (`workflow_dispatch`). This is the family test standard (the same gates the WCP repo runs; see `docs/TESTING.md`), restructured for speed by PORTS.md card 70 in `ncs-astro-sanity-starter`. Before, two serial-ish jobs built the site three times per PR (the build job, Playwright's `webServer`, Lighthouse). Now the site is built once and the gates run in parallel:

```
static --+                       (drift check, audit, typegen, types, check, lint, format, unit)
site ----+-> build (aggregator)   (build once, link check, upload dist/client)
         +-> e2e x3 shards -> test (aggregator)
```

**`build` and `test` are the REQUIRED status checks** (ruleset "main: PR + green CI"). They are now cheap aggregator jobs (`if: always()`, they fail unless everything behind them succeeded), so keep those two job names, and never put a `paths:` filter on `ci.yml`: a required check that never reports blocks the merge forever.

The `static` job ("Static checks"):

1. **Install** (`npm ci --no-audit --no-fund`).
2. **Canonical-file drift gate**: checks out the starter into `.ncs-starter`, runs `scripts/sync-check.mjs`, opens a proposal PR via `scripts/propose-drift.mjs` on drift, then deletes the checkout and fails the job if the check failed (the checkout must go before prettier/eslint sweep the tree).
3. **Public-data audit** (`scripts/public-data-audit.mjs`).
4. **Generate Sanity types** (three attempts: `sanity schema extract` intermittently core-dumps on the hosted runners), then **fail if `src/lib/sanity.types.ts` is stale** (`git diff --quiet`). The build does not run typegen, so the committed types must be regenerated by hand; this step catches the exact bug that shipped on 2026-06-14.
5. **Type check** (`npx astro check`), **lint** (`npm run lint`), **format check** (`npm run format:check`), **unit tests** (`npm run test:unit`, `node --test`).

The `site` job ("Build and links"): **Build** with `PUBLIC_SANITY_PROJECT_ID=""` so `sanityFetch` returns empty-state fallbacks (no credentials needed; the Studio is bundled into `/studio` by this same build), **internal link check** (`npm run check:links`, linkinator over `dist/client`; `/studio`, `/preview` and `/api` are skipped), then uploads `dist/client` as the one-day `dist-client` artifact.

The `e2e` job runs in 3 shards (`npm test -- --shard=N/3`), each downloading `dist-client` and running with `PLAYWRIGHT_SKIP_BUILD=1`, which makes `playwright.config.ts` (and `playwright.visual.config.ts`) serve that build instead of running `npm run build` again. Browsers (Chromium + WebKit) are cached by Playwright version (`actions/cache`, key `playwright-<os>-<version>`); on a hit only `npx playwright install-deps` runs. Shard 1 also runs **`npm run test:visual`** (the `/style-guide` screenshot diff against the committed Linux baselines) against the same downloaded build. A failing shard uploads `playwright-report-<n>`; shard 1 also uploads `test-results/` as `visual-diffs`. `update-visual-baselines.yml` is separate and unchanged.

**Re-cutting the shard weights.** Playwright's default `--shard` gives each shard a contiguous block of an EQUAL NUMBER of tests, in project order (all `chromium`, then all `webkit-iphone`), so the cheap tests cluster in one shard. The test step sets `PWTEST_SHARD_WEIGHTS: '37:67:35'` (colon separated, one weight per shard, an INTERNAL Playwright variable, so check it still works after a Playwright upgrade) to resize the blocks; no test is touched, and the blocks always partition the whole list, so a stale weight unbalances the shards but cannot drop a test. Measured before (runs 37157011093, 37158003175): test steps 44s / 7s / 42s and 46s / 11s / 50s, slowest shard 1.4x the mean. To re-cut after adding tests in bulk: build with `PUBLIC_SANITY_PROJECT_ID=''`, run `CI=1 PLAYWRIGHT_SKIP_BUILD=1 npx playwright test --reporter=json`, sum each test's duration in project-then-file order (the order `npx playwright test --list` prints per project), add about 8 units of cost to shard 1 for the visual step, and pick the block sizes that equalise the three sums (a brute force over two cut points is instant). Verify with `PWTEST_SHARD_WEIGHTS=a:b:c npx playwright test --list --shard=N/3` for N = 1..3: the counts must add up to the unweighted `--list` total.

Locally nothing changes: with `PLAYWRIGHT_SKIP_BUILD` unset, `npm test` still builds fresh, which is what stops a stale `dist/` passing. Do not set it locally.

**Lighthouse** is its own workflow (`.github/workflows/lighthouse.yml`) and is NOT a required check, so it is scheduled rather than blocking. It runs on: pull requests that touch score-moving paths (`src/**`, `public/**`, `scripts/**`, `lighthouserc.json`, `astro.config.mjs`, `wrangler.jsonc`, `package*.json`, the workflow itself), audited on a SAMPLE of 8 URLs, one per distinct template (home, about, courses, faculty, events, faq, style-guide, 404) passed as `--collect.url` flags; pushes to `main` with the same path filter and the FULL 15-URL list from `lighthouserc.json`; a weekly cron (Mondays 05:17 UTC, full list); and by hand (full list). `--collect.url` replaces only the URL list: the assertions and median-of-3 in `lighthouserc.json` are untouched (accessibility is a hard gate that must hold 100, LCP 4.5s and CLS 0.1 assert as errors, performance / best-practices / SEO warn at 0.85 / 0.95 / 0.95). A docs-only or workflow-only PR therefore runs no Lighthouse; keep the sample in step with `lighthouserc.json` when a new template ships.

## Sanity backups (`.github/workflows/sanity-backup.yml`)

Nightly (07:00 UTC) `sanity dataset export` of `production`, encrypted with `openssl`, uploaded as a GitHub artifact kept 14 days (day-level recovery; it was 90 until 2026-10-13, when the account-wide artifact storage quota filled). Two kinds: the Monday scheduled run and every manual run export documents + assets (`...-full.tar.gz.enc`); the other six nights export documents only (`...-docs.tar.gz.enc`, `--raw`: asset documents and references kept, files not downloaded), which is much smaller. Only the Monday full file is copied to R2 (when `BACKUP_R2_BUCKET` is set, newest 12 kept), and it covers anything older than 14 days. This is the safety net for a bad mutation or an accidental "Remove field" in Studio, neither of which is undoable otherwise.

**The encryption is load-bearing.** This repo is PUBLIC, so any logged-in GitHub user can download workflow artifacts. The dataset can hold directory and family content that must never be public, so the workflow encrypts the tarball before upload and the gate refuses to export at all when `BACKUP_PASSPHRASE` is missing — skipping a backup is recoverable, publishing the dataset is not.

**To activate:** add TWO repo secrets: `SANITY_AUTH_TOKEN` (a **read** token from sanity.io/manage is enough) and `BACKUP_PASSPHRASE` (a long random passphrase, e.g. `openssl rand -base64 32`). **Store a copy of the passphrase outside GitHub, somewhere the school/client can find it** — GitHub never shows a secret again, and a backup nobody can decrypt is no backup. The project's public id (`uz2sl3zp`) is hard-coded in the workflow since it is not a secret.

### Restore runbook

1. Download the `sanity-backup` artifact from the relevant Actions run and unzip it to get `sanity-backup-YYYY-MM-DD-full.tar.gz.enc` (or `-docs`; see the note after step 5).
2. **Decrypt** with the stored passphrase:
   ```bash
   BACKUP_PASSPHRASE=*** openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 \
     -in sanity-backup-YYYY-MM-DD-full.tar.gz.enc -out sanity-backup-YYYY-MM-DD-full.tar.gz \
     -pass env:BACKUP_PASSPHRASE
   ```
3. **Verify before overwriting.** Import into a throwaway dataset first:
   ```bash
   cd studio
   SANITY_AUTH_TOKEN=*** npx sanity dataset create restore-check
   SANITY_AUTH_TOKEN=*** npx sanity dataset import ../sanity-backup-YYYY-MM-DD-full.tar.gz restore-check
   ```
   Open the Studio against `restore-check` and confirm the content looks right.
4. **Restore to production** once verified (this overwrites, so be deliberate):
   ```bash
   SANITY_AUTH_TOKEN=*** npx sanity dataset import ../sanity-backup-YYYY-MM-DD-full.tar.gz production --replace
   ```
5. Trigger a production rebuild (push to `main` or `/rebuild`) so the live site picks up the restored content.

A `-docs` file relies on the referenced assets still existing in the dataset, which they do: Sanity assets survive document edits and "Remove field", and only an explicit asset delete removes one. Restore a `-docs` file into the same project and dataset only (the importer refuses asset documents that point at another dataset), so the throwaway-dataset check in step 3 needs a `-full` file. For a full restore use the latest Monday `-full` artifact, or the weekly R2 copy for anything older than 14 days (see the off-site step in the workflow).

## Uptime check (`.github/workflows/uptime.yml`)

Hourly, confirms the live site's key pages return 200; a failed run notifies you through GitHub. **To activate:** set the repo variable `SITE_URL` to the live origin (e.g. `https://www.presbyterianacademy.org`). GitHub's scheduler is best-effort, so for real monitoring also point a dedicated service (UptimeRobot's free tier) at the homepage.

## Form spam protection: Cloudflare Turnstile (since 2026-10-13)

The forms post to the site's own `/api/contact/` endpoint (starter card 45; `OPERATIONS.md`, "Form submissions"), which runs three checks, all server-side: a hidden honeypot field, a "faster than a person could type" timing check, and **Cloudflare Turnstile**. `FormRenderer.tsx` renders the Turnstile widget (explicit render, re-rendered on a light/dark toggle, `compact` below 300px wide so a 320px phone never scrolls sideways) and sends its token; the Worker verifies it against the `TURNSTILE_SECRET` secret. If the secret is unset the Worker skips the check, and if Turnstile's own API is down it lets the message through (the honeypot and timing check still apply), so an outage never eats a real enquiry.

This replaced hCaptcha-via-Web3Forms. Web3Forms gated Turnstile behind a paid plan, which is why hCaptcha was used before; owning the endpoint removes that constraint, and Turnstile's managed mode rarely asks a visitor to do anything.

- Widget: "PresAcad Contact Form" in the Cloudflare dashboard (Turnstile), managed mode, domain `presbyterianacademy.org`. Its sitekey is public and is the default in `FormRenderer.tsx`; `PUBLIC_TURNSTILE_SITEKEY` overrides it at build time.
- **Check the Cloudflare build variables for a stale `PUBLIC_TURNSTILE_SITEKEY`.** An older Turnstile setup in this repo used the same variable name before hCaptcha, and this page used to say "can be deleted" rather than "was deleted". A leftover value would override the new widget's key and the live widget would fail. Remove it, or set it to the new key.
- After launch, test with one labelled live submission and read the row back (`notified = 1`), never with a synthetic job that sends real mail.

## Secrets & variables summary

| Name                                             | Kind                                      | Used by         | Needed for                                                                     |
| ------------------------------------------------ | ----------------------------------------- | --------------- | ------------------------------------------------------------------------------ |
| `SANITY_AUTH_TOKEN`                              | secret                                    | sanity-backup   | nightly dataset backups (read token)                                           |
| `BACKUP_PASSPHRASE`                              | secret                                    | sanity-backup   | encrypts the backup artifact (public repo — required, keep an off-GitHub copy) |
| `SITE_URL`                                       | variable                                  | uptime          | hourly uptime check                                                            |
| `PUBLIC_TURNSTILE_SITEKEY`                       | build env (`.env` + Cloudflare), OPTIONAL | the forms       | overrides the live Turnstile sitekey baked into `FormRenderer.tsx`             |
| `TURNSTILE_SECRET`, `CONTACT_TO`, `CONTACT_FROM` | Worker secrets (`wrangler secret put`)    | `/api/contact/` | Turnstile verification and the notification email                              |

Repo secrets/variables live under GitHub repo Settings -> Secrets and variables -> Actions. The optional `PUBLIC_TURNSTILE_SITEKEY` is a build-time env, not a GitHub secret: set it where the site is built (locally and in Cloudflare). The form's Worker secrets live on the `presacademy` Worker, not in GitHub.

## Not done on purpose (revisit with scale)

Client-side error monitoring (Sentry), automated dependency PRs (Renovate / Dependabot), and a full alerting stack were left out: on a low-traffic, single-editor site they add more maintenance than they return. Worth adding once there is real traffic or a second editor.
