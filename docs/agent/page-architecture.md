# Page architecture

> Core page and section architecture, the page builder, the nav, and how empty content behaves.

## Page architecture

### Page structure

Each page is a Sanity singleton whose built-in copy and images are editable fields (with verbatim fallbacks, so the page reads correctly before anything is entered), plus auto-populated content from collections (courses, faculty, events, FAQ items). The layout of each page is fixed in code; the words, images, page-builder section order, and backgrounds are editable.

> **Editability caveat (2026-06-14).** The lay-school rebuild reused the church schemas, so not every section is editable yet, and Studio shows some orphan church-era fields. `content-editability-audit.md` is the ground-truth map of what is editable vs. hardcoded per page. The **home** and **about** pages were the worst offenders (most sections were hardcoded literals) and were re-schema'd this session: their built-in sections (home: wayfinding / stats / topics ticker / strip eyebrow-heading pairs / hero button labels / next-cohort label; about: mission / beliefs / how-we-teach / why / faculty-band) are now editor-driven Sanity fields with the literals as inline fallbacks, and `scripts/seed-page-copy.mjs` populated them so Studio mirrors the live site. Detail pages (course / faculty / event) also now render previously-orphaned fields (course syllabus download + seats note; faculty specializations / years / email; event all-day). Structural section labels ("At a glance", "Degrees", etc.) and the catalog/faculty filter legends are intentionally left hardcoded. **Update 2026-06-15:** the remaining dataset gaps were then closed by `scripts/seed-editability.mjs` (closing-CTA bands seeded on every page singleton, the missing contact/privacy/accessibility/404/events singletons + the faqItem/event collections created, 39 -> 63 docs); `content-editability-audit.md` has the current status.

**The page builder.** Every page singleton -- plus the generic `page` type -- has a `flexibleSections[]` array rendered by `SectionRenderer.astro` (called `Sections.astro` until 2026-10-27). Editors add / reorder / remove on-brand blocks (rich text, image+text, cards, quote, CTA band, form, feature cards, stats, FAQ, gallery, media showcase (slideshow/video), steps, logos, media feature, dynamic list incl. testimonials, resources/downloads, key dates, tuition tiers), each with a background control (brand tone, or image/video + readability overlay) via `SectionShell.astro`. They render below a page's built-in content and are empty by default, so nothing changes until used. Spec: `docs/superpowers/specs/2026-06-01-page-builder-expansion-design.md`.

**Built-in content + closing CTA.** A page renders its bespoke built-in sections (hero, then the page's content fields), then any `flexibleSections`, then a `<FinalCta>` whose eyebrow / headline / subhead are editable per page. The home page additionally supports the dated `seasonalHero` override and a "This Sunday" block.

### Empty-content behavior (no module toggles)

**Sanity is the single source of truth for all content** (see `editor-vs-hardcoded.md`): every content field is populated, so the Studio mirrors the live site, and the inline strings in the templates are only a safety net. This build also does not use the starter's `sectionVisibility` module-toggle system -- there are no opt-in module sections to gate. Content degrades gracefully on its own:

- **Empty fields fall back** to the built-in verbatim copy (the inline-fallback safety net), so a section can never go blank if a field is cleared. Fields are populated by default, so the Studio shows the live copy rather than a blank input.
- **Empty collections degrade** (e.g. `/sermons` shows a "watch online" state with the live link when no sermons are posted; an empty FAQ category simply doesn't render; an announcement only shows when enabled and within its date window).
- **Page-builder sections** are opt-in by nature: a page with no `flexibleSections` just shows its built-in content.

(If you later enable a starter module, its `docs/modules/` doc documents the visibility toggle that gates it.)

### Appearance controls (2026-08-28)

The "how does this section look" half of the page builder. All of it is enums and curated fields; there is no colour picker and no free-form CSS anywhere in the editing surface.

- **`src/lib/surfaces.ts` is the single source of truth.** It holds the six surface pairs (`default`, `warm`, `card`, `chapel`, `chapelDeep`, `ink`) and the three accents (`green`, `brass`, `ink`). Each surface names the CSS custom properties it resolves to per role (bg / text / heading / link) plus the literal hexes the Studio swatch dots draw with. `SectionShell.astro` reads it for classes, `src/sanity/components/SwatchInput.tsx` reads it for dots, and `src/lib/surfaces.test.ts` reads it for the **contrast gate**: every pair is measured against the real declarations in `globals.css`, in both themes, and must clear WCAG AA (4.5:1 body and links, 3:1 for the accent as a rule or as display text). A failing pair gets fixed; the threshold does not move.
- **The accent is wired once, at the shell.** `SectionShell` adds one class, and `globals.css` re-points `--section-accent` (the `.eyebrow` rule and `.heading-accent`) plus `--color-primary` / `--color-primary-dark` (every `bg-primary` / `bg-primary-dark` pill in the subtree). No block component carries an accent branch. The default accent emits **no class**, which is what keeps already-published sections byte-identical.
- **Rich twins** (`src/lib/inline-rich.ts`, `InlineRich.astro`). Seven curated plain-string support fields gained a sibling `<name>Rich` portable-text field restricted to `strong` + `em`. The renderer prefers the twin when it holds text and otherwise renders the string exactly as before; the plain field hides once the twin is filled. Headlines are deliberately excluded.
- **Accent words in headings** (`src/lib/heading-accent.ts`). The colour sibling of `scriptAccent`. Note the stega trap: in preview both the heading and the accent word arrive with invisible marker characters, so both sides are stripped with `plain()` before matching, and on a hit the CLEANED heading is what renders (which costs click-to-edit on that one heading, in preview only, only when an accent is set).
- **New enum fields go in `NON_STEGA_FIELDS`** (`src/lib/cms-preview.ts`). `accent` and `headingAccent` were added there; `tone` and `padding` were already listed.

### Header + footer nav (the masthead and the back cover, 2026-10-13)

The menus are **editor-driven**: `siteSettings.navItems` is the top menu (masthead nav strip, condensed bar and the phone Contents menu), and `siteSettings.footerColumns` plus `siteSettings.legalNav` feed the footer index. The built-in fallbacks live in `src/lib/siteSettings.ts` (`FALLBACK_NAV_ITEMS` is Courses, Faculty, Pricing, Events, Resources, About) and render only when those fields are empty. See `editor-vs-hardcoded.md`.

**The masthead** (`Header.astro`, "Foundation, edit with care"). Top to bottom: the spine strip (eight cover colours); the green top bar with the issue line from `getNextTerm` via `getChromeData()` (`issueLine` in `src/lib/term-issue.ts`: phones "Spring 2027 · first class 26 Jan", tablets the term and its state, desktops the whole line; the tagline when no term is scheduled), "Visit a class, free" (to `/get-started/`) and the Light / Dark control (`ThemeToggle.tsx`, md up); the nameplate row (one-line Fraunces nameplate, a mono subline from the tagline and town, then on lg up "Spring 2027 issue" with three fanned covers and the header button); and on lg up the ruled nav strip (`MastheadNav.astro`) with a mono note built from the real course and faculty counts (`navNote` in `src/lib/chrome.ts`). Everything beyond siteSettings comes from ONE memoized request, `getChromeData()` in `src/lib/queries.ts` (next term, counts, cheapest tier, every course's cover fields).

**The condensed bar.** The masthead stays in normal flow and never shrinks (that would be layout shift). A separate bar after `</header>` (nameplate, term tag, nav, button on lg up; nameplate and a Contents button on phones) is `position: fixed` and slides in with `transform` once an IntersectionObserver sees the masthead's foot sentinel ABOVE the viewport. While hidden it is `aria-hidden`, `inert` and `visibility: hidden`; reduced motion shows it without the slide. It lives outside `<header>` because the header carries a `view-transition-name`. Measured CLS while scrolling: 0.

**The Contents menu** (`MobileNav.tsx`, below lg). A full-screen Radix Dialog (shadcn Sheet parts): dialog semantics named by its "Contents" heading, focus trap, Escape, focus back to the opener, native scroll lock. Each row ends in a mono fact from `menuFact` in `src/lib/chrome.ts`: Courses, Faculty and Pricing are counted from the data ("8 this year", "5 teachers", "from $95"); every other row reads its link's new optional **`menuNote`** field (shown in Studio only on top-menu links), with built-in notes as the fallback. A shelf of up to six tiny covers links to courses. The condensed bar's Contents button opens the same dialog through a document click listener on `[data-open-contents]`.

**The back cover** (`Footer.astro`). Spine strip, the optional newsletter sign-up (only when `siteSettings.newsletter.enabled`), then Colophon (nameplate, `mission` + "published each term in {town}, and made possible by the {funder}" from `siteSettings.funder`, and a Where / Office / Write list with a Directions link), Index and In this issue (the next term's lead cover, "{Eight} courses, first class {date}", "Browse the issue", an outline header-button twin), and a mono bottom line (copyright, type credit, designer credit). The **Index** is every footer column link plus the extra links (Privacy, Accessibility), de-duplicated by address and sorted A to Z by `buildIndex` in `src/lib/chrome.ts`; the column headings in Studio no longer print. It flows in two **CSS columns**, never a row-wise grid, so the DOM order (what a screen reader hears) stays alphabetical. Phones stack Colophon, In this issue, Index with CSS `order`.

The desktop nav is **server-rendered** (gotcha #5) in `MastheadNav.astro`, drawn twice (strip and bar): flat items are real `<a>` tags, dropdown groups are native `<details>`/`<summary>` disclosures with real `<a>` children. A small progressive-enhancement `<script>` in `Header.astro` adds open-on-hover, close-on-outside-click, close-on-Escape and close-on-navigation (each group bound once; document listeners guarded by `window.__headerNavBound`). The nav works with JS disabled. The current page carries `aria-current="page"`, drawn as the green underline.

**Do NOT regress the desktop nav to a client-only island.** An earlier pattern hydrated a `NavDropdowns.tsx` React island with `client:only="react"`, which left the ENTIRE desktop nav out of the server HTML -- bad for SEO and CLS. Keep the flat links and the group structure SSR'd.

**Header breakpoint is `lg:` (1024 px).** Below it the masthead shows the nameplate and the Contents button; from lg the issue link, the button and the nav strip appear. Between lg and xl the nameplate, the bar nav and the gaps tighten and the nav note and term tag hide, so six links fit at 1024.

**Visibility on wrappers.** The chrome classes (`.mast-btn`, `.mast-nav`, `.contents-btn`) set `display` in unlayered CSS, which beats Tailwind's layered `hidden`. Put `hidden lg:block` and friends on a wrapper element, never on the chrome element itself.
